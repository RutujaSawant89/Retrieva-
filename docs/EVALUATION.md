# Evaluation

Retrieva measures retrieval and answer quality with an evaluation framework built into the
product (Evaluation page and `/api/v1/evaluation/*`) and with offline benchmarks on public
datasets. **Every number reported anywhere in this repository comes from an executed run**;
the reports in `evaluation/reports/` are generated by the scripts that produced them.

## In-product evaluation

1. **Dataset** — questions labelled with the passages (verbatim snippets) or documents that
   answer them, optionally with a reference answer. JSON, JSONL or CSV; uploading an existing
   name creates a new version (versions are immutable).
2. **Experiment** — one or more named retrieval configurations, either a preset or custom:

   | Preset | Compares |
   | --- | --- |
   | `retrieval_strategies` | BM25 vs dense vs hybrid (RRF) vs hybrid + cross-encoder rerank |
   | `fusion_weights` | Dense-heavy vs balanced vs BM25-heavy RRF weights |
   | `query_techniques` | Plain vs + pseudo-relevance-feedback expansion vs + multi-query |
   | `top_k` | Reranking candidate pool of 10 / 40 / 100 |

   Chunking and embedding-model comparisons are run by reprocessing documents with a different
   chunking configuration (or deploying a different embedding model) and re-running the same
   dataset version; each run records the chunking settings and model versions it used.
3. **Run** — every question goes through the real pipeline against the organization's indexed
   documents (optionally restricted to specific documents). Each run stores the dataset
   version, embedding/reranker/LLM versions, the full retrieval configuration, per-question
   results (retrieved passages with relevance flags, answer, metrics, latency) and aggregates.

### Metrics

| Metric | Definition | Needs |
| --- | --- | --- |
| Precision@K | relevant retrieved items in the top K ÷ K | labels |
| Recall@K | labelled targets found in the top K ÷ number of targets | labels |
| MRR | 1 ÷ rank of the first relevant item | labels |
| nDCG@K | DCG@K ÷ IDCG@K with binary gains; only the first item satisfying each target earns gain, so a target split across overlapping chunks is not double-counted | labels |
| Context precision | Σₖ Precision@k · relₖ ÷ relevant items retrieved (rank-aware precision, RAGAS definition) | labels |
| Context recall | reference-answer sentences supported by the retrieved passages ÷ reference sentences | reference answer |
| Faithfulness | answer claims supported by the retrieved passages ÷ answer claims | generation |
| Answer relevancy | cosine similarity of question and answer embeddings — an approximation of RAGAS answer relevancy (no question regeneration) | generation |
| Citation precision | valid citations whose passage supports the claim ÷ valid citations | generation |
| Citation coverage | factual answer sentences supported by a cited passage ÷ factual sentences | generation |
| Hit rate, abstention rate, latency (mean, p95) | | |

A retrieved chunk counts as relevant when it contains a labelled passage verbatim (after
whitespace and punctuation normalisation) or contains at least 80% of its tokens — robust to
chunk boundaries — or when it belongs to a labelled document.

"Supported" uses the same support scorer as the citation verifier (lexical precision of the
claim's content words in the passage blended with best-sentence embedding similarity, threshold
0.55; or an NLI cross-encoder when `VERIFIER_NLI_MODEL` is set). It is a heuristic judge;
treat faithfulness numbers as comparable across configurations rather than as absolute truth.

**RAGAS.** With `uv sync --extra ragas` and an OpenAI-compatible LLM configured, enabling
`use_ragas` additionally computes RAGAS faithfulness, response relevancy and (with reference
answers) LLM context precision/recall, stored under `metrics.ragas`. If RAGAS is unavailable the
run records why; no placeholder values are written.

## Offline benchmark: BEIR

`evaluation/benchmarks/beir_benchmark.py` runs Retrieva's own components in-process — the BM25
implementation, the embedding model, Reciprocal Rank Fusion and the cross-encoder — on a BEIR
dataset with official relevance judgments, reporting nDCG@10, Recall@100, MRR@10 and P@1:

```bash
cd backend
uv sync --extra dev --extra ml --extra bench
uv run python ../evaluation/benchmarks/beir_benchmark.py --dataset scifact
```

Results: [`evaluation/reports/beir_scifact.md`](../evaluation/reports/beir_scifact.md).

## Sample corpus benchmark

`evaluation/datasets/sample_corpus/` contains three fictional company documents (contract,
security policy, handbook) and `evaluation/datasets/northwind-qa.json` 18 hand-labelled
questions. `evaluation/benchmarks/run_sample_evaluation.py` uploads them through the API, runs the
`retrieval_strategies` preset scoped to those documents, and writes
[`evaluation/reports/northwind_strategies.md`](../evaluation/reports/northwind_strategies.md).
The corpus is small, so differences between strategies are less pronounced than on BEIR.

## Reproducing results

* Benchmarks are deterministic given the same model versions (embeddings are normalised, ranking
  is stable on ties). Latency depends on hardware; reports state the machine they ran on.
* In-product runs store everything needed to reproduce them (dataset version, configuration,
  model versions, chunking settings).
